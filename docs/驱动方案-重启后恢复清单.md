## 结论：驱动可用，但此前的归因是错的

### 驱动确实工作（实测）

| 检查 | 结果 |
| --- | --- |
| `create_context` | ✅ 成功 |
| 设备枚举 | 10 个鼠标（11–20）、10 个键盘（1–10） |
| `MouseStroke` 封送大小 | 20 字节（与 `interception.h` 一致） |
| `move (400,300)` → 读回 | ✅ **(400,300)**，精确 |
| 点击浏览器按钮 | ✅ 激活，页面计数 0→1 |

### 但"SendInput 点不中"这个结论是错的

我此前多次断言 SendInput 无法激活浏览器按钮，并据此论证必须上驱动。头对头对比
（同一控件、同一屏幕坐标、两条路径各点一次）：

```
SendInput activated the control : true
Driver    activated the control : true
```

**两条都打中。真正的故障一直是坐标换算。**

`CONTENT_OFFSET` 我记成"相对窗口的 (11,80)"，而调用方又加上了窗口原点，
等于**把窗口位置算了两遍**，每次点击偏出 (40,30)。点击照常投递、应用照常收到，
只是落在别处——**没有任何报错**。这正是这类自动化最难查的失败模式。

### 驱动为什么仍然值得保留

不是因为它修好了瞄准错误，而是因为它在输入栈里的**位置更低**：
对把合成输入当另一类事件的目标（游戏、直接读 Raw Input 的软件），
它是唯一能用的路径。**它是兜底，不是修瞄准错误的补丁。**

## 交付内容

| 文件 | 作用 |
| --- | --- |
| `src/bin/interception-input.ps1` | `probe`/`move`/`click`/`point`，走驱动 |
| `src/bin/interception-probe.ps1` | API 可达性与结构体尺寸自检 |
| `src/core/automation.mjs` | `driverInput()` / `driverAvailable()` / `measureContentOffset()` |
| `tests/automation.test.mjs` | 7 个测试用实测值锁定换算，含"窗口位置只能算一次" |

**坐标换算（已用实测值锁定）**：

```
屏幕 = 窗口位置 + 内容区偏移(11,80) + client 坐标
例：  (40,30) + (11,80) + (132,54) = (183,164)   ← 实测吻合
```

`measureContentOffset()` 可以一键反解真实偏移：点一下、让应用报落点、相减即得，
并且把**"点击没到达"与"偏移算错"区分开**——这两者症状相同但修法完全不同。
