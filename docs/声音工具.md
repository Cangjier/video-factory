# 声音工具（`video_audio_build` / `video_audio_measure`）

> **重组后注意（2026-10-04）**：本文写于工具重组之前，当时 12 个 action 同属 `video_audio`。现在按用途拆成两个工具：**`video_audio_build`** = `tone` `assemble` `restore` `record`，**`video_audio_measure`** = `identify` `speech_map` `loudness` `levels` `integrity` `sync` `noise` `devices`。每个 action 的行为、参数与返回结构未变；`tone` 必需的 `durationSeconds`、`restore`/`record` 的 `measure`、`restore` 的 `source` 已在重组中补进 schema（此前代码在用但未声明）。重组说明与 18 条缺陷清单见 [工具重组方案.md](工具重组方案.md)。

`video_audio_build` / `video_audio_measure` 合计 12 个 action，覆盖声音的五个角度：**创建、识别、质量、录制、噪音**。它只做两类事：

1. **测量**：读文件、报数字，不改文件；
2. **按你给的参数造文件**：生成信号、拼装音轨、应用修复链，然后把"写出了什么"再测一遍报给你。

它不会说"这段声音好听"，也不会自动选参数。凡是会影响听感的决定（哪一段放哪、噪声底该设多少、用不用降噪）都必须由你显式给出，或者在返回值里作为一个数字交给你判断。

## 确定性契约

| 保证 | 含义 |
| --- | --- |
| 同输入同输出 | 除 `record` 外，所有 action 都是 ffmpeg 的纯函数式调用；生成噪声必须给 `seed`（默认 1） |
| 参数字面回显 | 每个 action 的返回值里都有 `resolved` / `filters` / `args`，也就是**实际执行的那条命令** |
| 无网络、无模型 | 不调用任何云端服务；`transcribe` 与 `audio_events` 属于另外两个工具族 |
| 不替你做审美判断 | 阈值（静音门限、削波门限、门限电平、降噪量）都是参数，报出来的也是这些参数下的结果 |
| 产物自检 | `tone` / `assemble` / `restore` / `record` 写完文件后重新解码，比较"声明时长 / 解码采样数 / 期望采样数" |

`record` 是唯一的例外：命令是确定的，房间不是。所以它把这次录到的**时长误差、峰值、噪声底、工频能量**一起报出来。

## 创建

### `tone`

写一个完全指定参数的测试信号。

| 参数 | 说明 |
| --- | --- |
| `kind` | `sine` / `sweep`（线性扫频）/ `silence` / `white` / `pink` / `brown` |
| `frequencyHz`、`sweepToHz` | 频率、扫频终点；必须小于奈奎斯特频率，否则拒绝而不是混叠 |
| `durationSeconds` | 时长（必填） |
| `sampleRate`、`channels` | 默认 48000 / 2；`channels` 只允许 1 或 2 |
| `levelDbfs` | 标称电平，默认 -3 |
| `seed` | 噪声种子，默认 1 |
| `bitDepth` | `s16` / `s24` / `f32` |

正弦与扫频用 `aevalsrc` 生成，不用 ffmpeg 的 `sine` 源：本机这个构建的 `sine` 源输出比满刻度低约 18 dB，用它"设置 -6 dBFS"会静默地得到 -24 dBFS。`aevalsrc` 按构造就是满刻度，所以 `levelDbfs` 说了算——实测 -6 dBFS 的正弦峰值误差 < 0.05 dB。

### `assemble`

把若干片段放到同一条时间轴上，**以采样点为单位**，然后报告写出的文件。

```jsonc
{
  "action": "assemble",
  "clips": [
    { "source": "narration/s01/voiceover.mp3", "at": 0.25 },
    { "source": "narration/s02/voiceover.mp3", "at": 12.9, "until": 9.2 }
  ],
  "totalSeconds": 30,
  "sampleRate": 48000,
  "channels": 1,
  "overlap": "reject"
}
```

- **放置不用 `adelay`**。毫秒级的 `adelay` 每次拼接会差几十个采样点，十几段之后就是可听见的偏移。这里用 `atrim=start_sample/end_sample` + `concat` + `apad=whole_len`，位置就是采样点编号。
- `until` 用来切掉片段自身尾部的静音（edge-tts 每段都会带 0.8 s 左右），`at + until` 就是该段的终点。
- `overlap` 默认 `reject`：有重叠就**拒绝执行**并列出重叠的片段与秒数。`sum` 会相加（`amix normalize=0`），这几乎总是两个人同时说话，所以必须显式要求。
- 片段终点超过 `totalSeconds` 时，`concat` 模式会拒绝；`mix` 模式会截断并把 `verification.truncatedByTimeline` 标为 true。
- 返回值里的 `verification.exact` 为 `true` 表示解码出的采样数与计划**完全一致**（WAV 输出时应当总是 true）。

写出的文件旁边会有一份 `<文件名>.manifest.json`，内含位置表、滤波器串和验证结果。

## 识别

### `identify`

一个文件**声明**什么，和它**实际交付**什么。

- `declaredSeconds`：容器/头部声明的时长；
- `decodedSeconds`：解码器逐帧解出来的采样数 ÷ 采样率；
- `decodedVsDeclaredSeconds` / `decodedVsDeclaredPercent`：两者之差——这是最有用的一个数，丢了 20% 帧的文件会在这里露馅；
- `decodeErrors` + `errorSamples`：解码器抱怨了几次、长什么样；
- `spectrum.bandwidth`：有效带宽（相对最响 bin 下降 20 dB 的位置）——48 kbps 的 24 kHz MP3 大约在 11 kHz 截断，96 kbps 明显更高；
- `spectrum.tilt`：四个频段的 dB/octave 斜率（20–120 / 120–500 / 500–4k / 4k–12k）；
- `answeredBy`：`ffprobe` 还是 `ffmpeg` 回答的（见下面"环境坑"）。

### `speech_map`

`silencedetect` 判定的语音与静音区间，外加 `speechSeconds` / `silenceSeconds` / `speechRatio` / `longestGap`。阈值（`noiseDb`，默认 -40 dB）与最短静音（`minSeconds`，默认 0.25 s）都回显在结果里——换阈值结果就换，这是测量而不是判断。

要做声学类别（音乐/语音/环境声）划分，用 `video_analyze {action:"audio_events"}`。

## 质量

### `loudness`

EBU R128：`integratedLufs`、`loudnessRangeLu`、`truePeakDbfs`、`thresholdLufs`、`lraLow/High`，外加 ffmpeg `astats` 的每声道统计（峰值、RMS、直流、噪声底、entropy）。给 `paths` 传多个文件时，额外给出：

- `spreadLu`：最响与最轻之差。逐段合成的配音经常在这里露出 5–7 LU 的落差，听起来就是"有一段突然变响"；
- `outliersBeyond.thresholdLu`（默认 2 LU）+ `files`：偏离中位数超过该阈值的文件清单。它只是清单，好坏仍由你判断。

`timeline: true` 会附上按秒折叠的短时响度时间线，以及最响/最轻的那一秒。

### `levels`

采样域事实，**按文件自身的采样率解码**（不重采样，所以削波不会被抹平）：

- `peak` / `peakDbfs` / `rmsDbfs` / `crestFactorDb` / `dcOffset`；
- `perChannel`：每声道峰值、RMS、直流；
- `clipping`：`totalHighSamples` 是精确总数，`runs` 列出每段削波的起点、长度、峰值（默认阈值 0.999、最短 3 个采样点、最多列 200 段）；
- `timeline`：每秒的 RMS（dBFS）。一个 1 kHz 满刻度正弦会显示"每秒都接近 0 dBFS"，而在 1 s 与 3 s 有声音的拼装结果会显示第 0/2/4 秒是 `-inf`。

`maxSeconds` 默认 600：更长的文件请用 `start`/`duration` 分段，或接受"只分析前 600 秒"并在 `truncatedAtMaxSeconds` 里看到它。

### `integrity`

**这个 action 是为一个真实的 bug 写的**：edge-tts 返回的音频曾经在每个 `Path:audio` 消息前面多带一个 `\r\n`，客户端按 `headerLength` 切片时把这 2 字节留在了文件里，于是每 720 字节（5 个 MP3 帧）出现一个 2 字节缺口，解码器每个缺口报废一帧——**20% 的音频消失**，听起来"生涩、不连贯、不清晰"，而且整段比时码短 20%，拼进视频后最后一句没有声音。

它报三件事：

1. **帧链**：`frameWalk.breakCount`、`gapHistogram`（缺口大小直方图）、`breaks[].bytes`（缺口里究竟是什么字节——`0d0a` 和随机损坏含义完全不同）、`estimatedLostFrames` / `estimatedLostSeconds`；
2. **解码采样数**：`decodedSeconds` 与 `declaredSeconds` 的差；
3. **解码器抱怨**：`decodeErrors`。

`repair: true` + `repairPath` 会写出一份修复副本（**原文件绝不改写**）：只删除帧与帧之间的窄缺口（默认 ≤ 64 字节），帧本身一个字节都不改。首部的游离字节和尾部的残帧会被删除并分别记在 `droppedLeadingBytes` / `droppedTrailingBytes`；如果发现"缺口后面还有帧"的宽损坏，它会**拒绝**并报出偏移，而不是静默丢弃后半段音频。

非 MPEG 音频（AAC、FLAC、PCM）时 `frameWalk.applies` 为 false，逐帧检查不适用，请以 `decodedVsDeclaredPercent` 与 `decodeErrors` 为准。

### `sync`

两条"同一段话"的录音之间的**偏移**与**漂移**。

- 先按包络做互相关（语音的起止形状在两次编码后仍然一致，波形则完全对不上），再用逐采样点相关细化；
- `offsetSeconds` 正值表示 `comparison` 比 `reference` 晚；
- `windows[]` 是沿时间轴均匀取的若干窗口的偏移，`drift.ppm` 是它们的最小二乘斜率（每百万秒的漂移）；
- `correlation` 低于 0.3 时这个偏移不可信，结果里明确写了这一点。

## 噪音

### `noise`

噪声底由什么构成，分三件事报，因为三件事的修法完全不同：

- `broadband`：整体均值 RMS、最响窗口、最安静窗口及其时间；
- `hum.harmonics[]`：50 Hz 与 60 Hz 两族的 1–8 次谐波，逐频用 Goertzel 精确测量（dBFS 与线性幅值），`dominantFamilyHz` 是能量更大的一族，`sum50HzDb` / `sum60HzDb` 是各族总能量；
- `spectrum`：取自**最安静的那个窗口**（在有人说话的窗口里量噪声，量到的是人声）——有效带宽、四段 tilt、以及最强的若干窄带峰（`tonalPeaks`，带突出度）。

频谱分析在 48 kHz 上做。这不是细节：在 8 kHz 上分析，"这个文件的有效带宽"永远只会报 4 kHz。

### `restore`

一条**显式**的修复链，每一步的参数都写出来，执行完再测一遍写出的文件。

```jsonc
{
  "action": "restore",
  "target": "audio/take.wav",
  "steps": [
    { "method": "highpass", "frequencyHz": 80 },
    { "method": "dehum", "mainsHz": 50, "harmonics": 3, "widthHz": 4 },
    { "method": "denoise", "noiseFloorDb": -45, "noiseReductionDb": 12 }
  ]
}
```

| method | 参数 | 生成的滤波器 |
| --- | --- | --- |
| `denoise` | `noiseFloorDb`(-80..-20) 或 `trackNoise:true`、`noiseReductionDb`、`noiseType` | `afftdn=nr=..:nt=..:tn=..:nf=..` |
| `dehum` | `mainsHz`(50/60)、`harmonics`(1..12)、`widthHz` | 每个谐波一个 `bandreject=f=..:width_type=h:w=..` |
| `notch` | `frequencyHz`、`widthHz` | 单个 `bandreject` |
| `gate` | `thresholdDb`、`rangeDb`、`ratio`、`attackMs`、`releaseMs`、`mode` | `agate`（dBFS 自动换算成 ffmpeg 要的线性幅值） |
| `highpass` / `lowpass` | `frequencyHz`、`poles`(1/2) | `highpass` / `lowpass` |

返回 `before` / `after` / `change`：峰值、RMS、噪声底、50 Hz 与 60 Hz 总能量的变化、带宽变化。**"噪声底几乎没变但听感变化很大"通常意味着问题在工频或某个窄带峰上，不在宽带噪声上**——这正是把三者分开报的原因。

没有 `arnndn` 之类的模型降噪默认值：本插件不附带模型文件，要用请显式给 `model`（该滤波器在本机构建里可用）。

## 录制

### `devices`

列出 DirectShow 报出的采集设备，音频与视频分开，每个设备给出 `name`（照原样传给 `record`）与 `alternative`（语言无关的稳定标识）。`supported` 表示这个 ffmpeg 构建有没有编译 dshow。没有设备是正常结果，不是错误：`audio: []` 加一句原因。

### `record`

从**指定名字**的设备录固定秒数，然后测这一条：

- `measuredSeconds` 与 `durationErrorSeconds`：明显为负说明设备启动慢、开头被吃掉；
- `measured.peakDbfs` / `rmsDbfs` / `dcOffset` / `peakCount`：峰值贴近 0 说明过载，先降增益再录；
- `noise.noiseFloorDb` 等：录完之后房间本底是多少；
- `deadlineSeconds`：进程在 `seconds + 20` 秒时被强杀，不会挂住。

一次最多 3600 秒；默认写 `audio/record-<本地时间戳>.wav`（录音是"条"，不该互相覆盖）。

## 环境坑（都已在实现里处理）

1. **`sine` 源电平不对**：本机 ffmpeg 构建的 `sine` 源比满刻度低约 18 dB。生成正弦/扫频改用 `aevalsrc`，`levelDbfs` 才是可信的。
2. **ffprobe 会把某些 WAV 误判成 MPEG-TS**：48 kHz 单声道、内容恰好长得像 TS 同步字节的 WAV，`ffprobe` 报 `End of file` 退出，`ffmpeg` 自动探测也一样。处理方式：`describeAudio` 先试 ffprobe，失败就改读 ffmpeg 的输入报告；`runAudio` / `decodePcm` 在自动探测失败时按**文件头**（`RIFF/WAVE`、`ID3`、`0xFFEx`、`ftyp`、`fLaC` …）显式指定 `-f` 重试一次。结果里会带上 `answeredBy: "ffmpeg"` 或 `forcedFormat: "wav"`，不隐藏这件事。
3. **`astats` 走 logger**：`-v error` 下它什么都不打印。所有统计读取都用 `-v info -nostats`。
4. **edge-tts 每段带 0.8 s 尾巴静音**：这是服务端行为（上游 edge-tts 用固定的 8,750,000 ticks ≈ 0.875 s 补偿它）。逐段拼装时要么用 `until` 切掉，要么把它算进场景长度。

## 典型用法

```jsonc
// 1. 逐段配音拼成一条音轨：放在各自的起点上，砍掉尾巴静音，时间线给足
{ "action": "assemble", "clips": [ /* {source, at, until} */ ], "totalSeconds": 140.234,
  "sampleRate": 48000, "channels": 1, "overlap": "reject" }

// 2. 先确认文件没坏，再谈听感
{ "action": "integrity", "target": "narration/voiceover.mp3" }
{ "action": "integrity", "target": "narration/s08/voiceover.mp3", "repair": true,
  "repairPath": "narration/s08/voiceover.fixed.mp3" }

// 3. 逐段响度对齐：找出偏离中位数超过 2 LU 的那几段
{ "action": "loudness", "paths": ["narration/s01/voiceover.mp3", "/* ... */"] }

// 4. 弄清噪声是什么：宽带？工频？某个窄带峰？
{ "action": "noise", "target": "audio/take.wav", "mainsHz": 50 }

// 5. 只处理你确认过的那一项，然后看它改了多少
{ "action": "restore", "target": "audio/take.wav",
  "steps": [{ "method": "dehum", "mainsHz": 50, "harmonics": 3 }] }

// 6. 录一条环境本底，用同一套测量去看它
{ "action": "devices" }
{ "action": "record", "device": "<devices 里的 name>", "seconds": 10 }
```
